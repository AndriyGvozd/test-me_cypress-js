## 3. Поза обсягом
Орієнтир ТЗ — 2–3 години, «якість важливіша за кількість». Тому UI-кейси (12) покривають лише критичний функціонал: гроші, замовлення, дані користувача, ізоляцію та безпеку. API покрито повністю (20 кейсів): кожен ендпоінт зі схеми має власну перевірку, бо API-тести швидкі й стабільні. Нижче — що свідомо не покрито і чому.

### 3.2 Важко відтворити в межах часу
| Що не покрито | Причина |
|---|---|
| Прострочений token → 401 (API та поведінка UI) | Token живе 24 год; прострочений не створити на вимогу. Поведінка UI при 401 у ТЗ не описана |
| Reset не відкликає token в іншому браузері (UI) | Потребує двох браузерів з одним token. На рівні API те, що старий token працює після створення нового, перевірено (TC-API-20) |

### 3.3 Другорядний функціонал (нижчий пріоритет)
| Що не покрито | Причина |

| Видалення останнього товару → порожній кошик | Низький ризик; стан UI |

### 3.4 Не покрито, бо очікуваний результат не визначено в ТЗ
| Що не покрито | Причина |
|---|---|
| Коди відповіді для невалідних значень, яких немає в ТЗ (неіснуючий товар в обраному, дублікати позицій у кошику, `status=foo`, неіснуючий order_id) | Очікуваний результат був би припущенням; тести мають перевіряти вимоги, а не здогадки |
| Реакція UI на min > max (повідомлення чи блокування) | ТЗ задає правило, але не описує поведінку інтерфейсу; перевірено на рівні API |

Усі пункти можна додати наступною ітерацією: спершу 3.2, далі 3.1.

## 4. Ризики
- Спільний тестовий стенд, rate limit (30 середовищ/хв, 180 записів/хв) → де тест лише читає дані, одне середовище на `describe`; `cy.createWorkspace` при 429 чекає час із `Retry-After` і повторює запит.
- Навмисні дефекти → тести падають за задумом; кожне падіння описано в `BUGS.md`.
- Відсутність `data-testid` для частини елементів → стабільні `id` і `data-*` атрибути застосунку, селектори зібрані в Page Objects.
- Токени середовища можуть потрапити в лог команд і на скриншоти → у перевірках token порівнюється як boolean, скриншоти-докази переглянуто вручну.

## 5. Підхід
- Кожен тест — у власному workspace (`cy.createWorkspace`, `cy.visitShop`).
- Очікувані суми рахуються еталонною функцією `expectedQuote`, а не беруться з відповіді застосунку.
- Техніки: класи еквівалентності, граничні значення, комбінації фільтрів.
- **Паралельний запуск.** `npm run test:parallel` ділить специфікації між workers (за замовчуванням 3) з балансуванням за кількістю тестів. Кожен worker створює власні token, як вимагає ТЗ. Прогін: ~2 хв 40 с послідовно → ~1 хв 30 с у 3 workers.

## 6. Критерії завершення
Тестування вважається завершеним, коли:
1. Усі кейси Critical і High (UI і API) виконані автотестами; статус кожного — Pass або Fail, без Blocked / Not run.
2. Кожне падіння класифіковано: або дефект застосунку (опис у `BUGS.md` з кроками, очікуваним і фактичним результатом, доказом), або помилка тесту — тоді тест виправлено.
3. Немає нестабільних тестів: повторний прогін дає той самий набір падінь, жоден тест не проходить лише з другої спроби (див. розділ 7).
4. Кожен ендпоінт API зі схеми має щонайменше одну перевірку.
5. Те, що не покрито, перелічено в розділі 3 з причиною.

## 7. Аналіз нестабільних тестів
Під час розробки знайдено три причини нестабільності. Усі вони були в тестах, а не в застосунку, і всі виправлені.

| # | Симптом | Причина | Виправлення |
|---|---|---|---|
| 1 | TC-UI-10: сортування «не працює», хоча вручну працює | Під час завантаження сторінка робить ще й запит `GET /api/products?limit=20` (без `page`). Glob-intercept `**/api/products*` ловив його, і кожен `cy.wait('@catalog')` прив'язувався до відповіді попередньої дії | Матчери звужено до запитів каталогу (`query: { page: '*' }`) і винесено в `support/api/routes.js` |
| 2 | Перевірки сум і цін падали, хоча на скриншоті значення правильні | Значення з DOM розбиралися через `cy.get().then(fn)`. `.then()` не повторює спробу, тож `.should()` перевіряв перший знімок DOM до перерендеру | Власна query-команда `parseWith` (`Cypress.Commands.addQuery`): перетворення перезапускається разом із `cy.get()`, доки перевірка не пройде |
| 3 | TC-UI-9 падав з першої спроби лише в паралельному прогоні | Після «Почати заново» застосунок записує новий token у `localStorage` асинхронно, вже після відповіді сервера. `cy.appState()` теж був на `.then()`, тож під навантаженням читав старе значення | `cy.appState()` переписано на ланцюжок query-команд (`window → its → invoke → parseWith`). Перевірено 3 прогонами без retry і паралельним прогоном: жодного повтору |
| 4 🆕 | TC-UI-15 (клавіатурне оформлення) пройшов лише з другої спроби в паралельному прогоні | Після введення адреси застосунок перераховує суму й на цей час вимикає кнопку «Оформити замовлення». `cy.focus()`, на відміну від `click()`, не чекає, поки елемент стане активним; під навантаженням перерахунок довший | Перед фокусом — `should('be.enabled')`. Знайдено під час фінального рефактору <!-- added: refactor --> |

Як відстежується: у `cypress.config.js` у run mode `retries: 1`. Тест, що пройшов лише з другої спроби, видно в лозі (`Attempt 1 of 2`) і за скриншотом `(failed)` без падіння в підсумку. Такий тест вважається дефектом тесту й розбирається, а не приховується повторами. В останньому паралельному прогоні кількість повторів дорівнює кількості справжніх падінь (8), тобто нестабільних тестів немає.

Що ще знижує ризик нестабільності: жодних фіксованих `cy.wait(ms)` (крім паузи за `Retry-After`); синхронізація через `cy.intercept` + `cy.wait('@alias')`; дані для UI-тестів готуються через API або storage; кожен тест має власне середовище.
